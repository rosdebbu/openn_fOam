00 / BackgroundCFD in five minutes, in your own code's terms

Computational Fluid Dynamics means solving the Navier–Stokes equations — the equations for how a fluid's velocity and pressure evolve — numerically, because they have no general closed-form solution. You chop the domain into a grid of cells, and march forward in small time steps, updating every cell from its neighbours.

Your solvers all use the same recipe, the projection method: each step, first move the velocity forward using momentum alone (advection + viscosity), which leaves a flow that doesn't conserve mass; then solve a pressure equation and subtract its gradient, which pushes the flow back to mass-conserving. You can see this literally in scripts/train_openzess_grpo.py lines 148–184: upwind advection, a Laplacian for viscosity, 15 Jacobi sweeps for pressure, then the projection subtraction.

Three dimensionless numbers decide whether it works, and all three appear in your code:

NumberMeaningRuleWhere it lives
Reynolds Reinertia ÷ viscosity — how chaotic the flow isinputν = 1/Re
Courant Co = U·dt/dxhow far fluid moves per step vs. cell size< 1validate_spec, capped 0.65
Diffusion ν·dt/dx²how far viscosity spreads per step≤ 0.25validate_spec

Those two guards are correctly implemented in backend/ai_simulate.py. Break either and the solution blows up to infinity within a few steps — which is why your code checks them before running anything.

The last concept is the one this whole audit turns on. A simulation is converged when you have marched forward long enough that the flow stops changing. Only then does it represent a real steady flow. The standard way to prove a 2D solver is correct is the lid-driven cavity: a square box, the top lid slides sideways, one big vortex forms. Ghia, Ghia & Shin (1982) published the exact centreline velocities for this case, so you compare your converged numbers against their table. Your repo does exactly this — and that comparison is finding 01.

02 / FindingsResearch integrity — fix before submission

blockingThe published “Max CFL” column is a default value, not a measurement

verify_cfd_physics() returns a key named cfl_max. The benchmark harness reads res.get("cfl", 0.0). The key never matches, so the fallback 0.0 is printed for every row — which is exactly what docs/IEEE_BENCHMARK_RESULTS.md shows: 0.000 on all four grids. A Courant number of zero is physically impossible for a flow that is moving.

scripts/run_ieee_benchmarks.py:42 ← scripts/train_openzess_grpo.py:218

blockingThe Ghia validation runs 12 time steps and is never converged

The verifier loops for _ in range(12), then interpolates the centreline and compares it to Ghia's table. At a 41×41 grid with the CFL cap, dt ≈ 0.016, so twelve steps is about 0.2 seconds of physical time. A Re = 100 cavity needs roughly 20–30 seconds to reach steady state. You are comparing a flow that has barely started against a converged reference.

The table proves it: RMSE goes 0.2200 → 0.2325 → 0.2381 → 0.2378 as the grid refines. Error rising with refinement is the signature of a solution that isn't converged — a correct solver shows the opposite. Right now the number mostly measures “the lid has moved a little and the rest of the box is still at rest”, which is why it barely changes with grid size.

Fix: march to a steady-state residual (loop until max |un+1 − un| < 1e-6, cap the iterations), and re-run. Expect RMSE to drop by an order of magnitude and to fall with refinement. That gives you a real grid-independence study. Keep the 12-step version as the fast RL reward only, and call it something else.

scripts/train_openzess_grpo.py:146, :215

blockingThe RL result measures JSON formatting, not physics

The reward gives physics credit only when ghia_rmse < 0.65. Because the un-converged verifier returns ≈ 0.23 for essentially every candidate, that term is saturated — the same bonus for a good spec and a bad one. The gradient the model actually receives comes from the remaining terms: valid JSON, allowed enum values, CFL arithmetic.

So “Base 33.3% → RL 100.0% valid JSON” is honest, and it is a formatting and constraint-satisfaction result. It is not evidence that GRPO taught a 0.6B model fluid dynamics. Framed the first way it is a perfectly publishable finding — small models can be RL-tuned to emit schema-valid, stability-constrained simulation specs. Framed as physics-verified RL, a reviewer who reads the reward function will reject it.

Six prompts cannot distinguish 100% from 83%. Minimum viable: 60–100 prompts, a held-out split the model never trained on, three seeds, and mean ± std. You have the generator for this already — SEED_PROMPTS plus the archetype/substance enums will produce hundreds of combinations cheaply.

03 / FindingsWhy the AI “doesn't run properly”

This is your actual bug, and it has four causes stacked on top of each other.

bugThe model's dependencies are not installed

requirements.txt lists fastapi, uvicorn, numpy, scipy, matplotlib, websockets. The Qwen endpoint imports torch, transformers and peft at first call. On any fresh environment that raises ImportError, the endpoint returns {ok: false}, and the UI prints “⚠️ Local Qwen3-0.6B unavailable”. That message is the symptom you have been looking at.

backend/app.py:683–685 vs requirements.txt

designThe adapter was trained for JSON and is being asked to chat

GRPO trained it against a system prompt that says “output ONLY a valid JSON object”. The chat endpoint hands it a different system prompt — “Help the user with OpenFOAM… be concise and practical” — and asks for prose. A 0.6B model fine-tuned hard onto one output format will produce near-garbage in another. Even with the dependencies fixed, this endpoint will read as broken.

The task it was trained for — turning a sentence into a simulation spec — is served by /api/ai/simulate, which doesn't use it. Swap them. Let the adapter produce the spec JSON, pipe it through validate_spec() (which already coerces and clamps), and fall back to the regex table when the JSON fails to parse. That is a genuine LLM-in-the-loop contribution, and it is the one your paper can defend.

backend/app.py:706 vs scripts/train_openzess_grpo.py:38

honestyThe “AI builds your simulation” path contains no model

/api/ai/simulate is a ten-entry keyword table — house, tower, box, f1, cylinder… first match wins. It is clean, well-commented, deterministic code and a reasonable product decision. It is not AI, and it must not be described as AI in the paper.

bugFirst request blocks on a 1.2 GB download, with no lock and no timeout

_get_qwen_rl() loads base weights from HuggingFace synchronously inside the request handler. The first user waits minutes or the request times out; two simultaneous requests load the model twice and can exhaust VRAM. Load at startup behind a flag, or pre-download and read from a local path.

04 / Findings“There is no chat feature”

AiAssistant.vue has an input box, an “Ask AI” button and a “Thinking…” state. It calls no model. 06 / AnswerHow does a user actually make their own simulation?

Two paths exist. Both work. They are separate systems and they never meet — which is why the platform feels like it can't do the thing it is for.

Path A — the Custom Geometry Builder (real, but local only)

Open the sidebar, find the Custom Geometry Builder card, pick one of six shapes, drag three sliders (x position, y position, size — plus angle of attack for the airfoil), press Apply. That emits obstacleSpec, which travels over the WebSocket to build_obstacle_mask() in solver.py. That function genuinely rasterizes all six shapes at your chosen position and size, and its docstring says so: “This is the pathway that lets users build their OWN simulations.” It is real, and it works — on localhost.

Path B — presets and “AI Run” (works on the web, but is a menu)

The viewer ribbon has a preset dropdown and the “AI Run” text box. Both resolve to one of eight hardcoded cases and run fvm_solver.wasm in the browser. No server needed. But you cannot place your own shape — except for two undocumented keywords: type “car” or “lander” and synthesizeCustomPrimitives() assembles a hardcoded four-primitive model. Nothing in the UI tells anyone those exist.

So the thing a user cannot do is the project's own premise

Build their own geometry and have it run in the browser. Fixing it is small, because both ends are already built: OpenFoamWasmEngine.applyCustomPrimitives() voxelizes arbitrary primitives straight into the WASM solver via fvm_paint_obstacle. It is simply only ever called from those two keyword matches. Write the coordinate adapter, call it from the builder's Apply button, and Path A runs with no backend at all. This is the highest-value change in the whole audit — it is the difference between a demo with eight slides and a platform.

What file upload actually does today

  • .vtk into the ParaView viewer — works. You can load and inspect an existing result.
  • .stl / .obj / .step — the dropzone accepts the file, then shows “📎 filename — not used” under the label “CAD import is not implemented yet”. Honest, but it means there is no geometry import.
  • An OpenFOAM case folder — no import path exists. Export only, and only the cavity geometry is correct.

Three keyword matchers stacked: synthesizeCustomPrimitives() (two regexes), then inferLocalPresetFromPrompt() (seven regex lines), then the backend's ten-rule table. bugThe Reynolds number is discarded, and the label claims otherwise

When “AI Run” changes the preset — the normal case — it assigns wasmPreset.value and lets the watcher do the work. The watcher is initPresetPreview(nextPreset) with no Reynolds override, and initPresetPreview then falls back to meta.re, the preset's hardcoded value. Meanwhile layaStatusText displays the Reynolds number it parsed from your prompt.

So the status reads Re=1000 while the solver actually ran at Re=200. The UI reports a number that was never used. One-line fix: pass the value through the watcher.

designThe chat physically cannot drive the WebAssembly simulation

The real chat lives in SidebarControls.vue, and its autonomous-action path writes obstacleSpec into the backend solver. The WASM engine in the viewer is driven only by the preset dropdown and the one-line “AI Run” box. There is no route from a chat message to the browser solver. So “chat with the model about my simulation” isn't a missing feature — it's structurally impossible in the current wiring, on top of the no-message-history problem from finding 04.

Once the adapter in Figure 2 exists, this becomes easy: the chat already extracts a shape spec, so point it at applyCustomPrimitives() too, and the same message can place geometry and run it in the browser.

07 / FindingsDeployment, safety, structure

bugThe deployed web version cannot have a backend, by construction

Two independent blocks. vercel.json ships only the static SPA — there is no Python runtime. And app.py deliberately restricts CORS to ^https?://(localhost|127\.0\.0\.1|\[::1\]), so even a separately hosted backend would reject the deployed origin. The “open web version anyone can use” is today the WASM solver plus the user's own cloud LLM key. That is a real, defensible product — just describe it as that.

To actually ship the backend: host it (Railway, Fly, Render), add the deploy origin to the CORS regex, and set VITE_API_URL at build time.

bugFive different conventions for the backend URL, three of them hardcoded

http://${window.location.hostname}:8000 appears literally in aiCopilot.ts, SidebarControls.vue and ParaViewGlanceViewer.vue; elsewhere the code sniffs for port 5173, or reads VITE_API_URL, or uses a relative path. On an HTTPS page the hardcoded http:// is blocked as mixed content. Collapse all five into one exported apiBase().

riskThe server can click, type and screenshot on this machine

/api/agent-desktop/click, /type, /screenshot and /launch-paraview drive the host desktop over plain HTTP with no authentication. The localhost CORS rule is the only thing protecting you, and CORS does not stop a non-browser client. Never expose port 8000 to a network, and put this behind an explicit opt-in flag that defaults to off.

gap84 backend tests; zero tests for the 15,852 lines where the product lives

The Python suite passes cleanly. But the WASM solver, the viewer, the AI copilot, the dictionary generation and the 3D stage have no tests at all. The two cheapest high-value tests: validate_spec / CFL clamping already has coverage — add one that asserts the WASM solver and solver.py agree on the cavity, and one that asserts parseVtkAscii rejects non-VTK input (finding above).

cleanupDead weight

  • Five orphaned Vue components — AiAssistant, HelloWorld, CfdCanvas2D, OpenFoamTerminal, OpenFoamDictEditor — roughly 800 lines with no importer.
  • Two orphaned solvers (#3, #6) — roughly 1,100 lines.
  • An internship scraper (/tracker, /api/internships/latest) living inside the CFD API server.
  • Over thirty PDFs and a 768 KB Overleaf zip committed at the repository root.
  • requirements-dev.txt pins httpx2>=2.0; FastAPI's TestClient wants httpx. Verify that this is the package you meant.

08 / CreditWhat is genuinely solid

Don't let the list above obscure these

  • The WebAssembly claim is true. fvm_solver.wasm is real Emscripten-compiled C with a proper C ABI — fvm_create, fvm_step, pointer accessors into the heap, obstacle painting, adaptive CFL. Plus a second module, fea_structure.wasm, for the structural side. Browser-native CFD with no server is the strongest thing in this project and it actually works.
  • The stability guards are correct. validate_spec caps dt at both the Courant and the diffusion limit, with the reasoning written in the comment. This is the part most student CFD code gets wrong.
  • Security decisions were made deliberately, not by accident. The CORS regex has a comment explaining that "*" would let any site call DELETE /api/projects. The Gemini key is sent in a header rather than the URL, with the reason stated. A previous bug that POSTed Anthropic keys to api.openai.com was found and fixed, and the fix is documented in place.
  • 84 passing backend tests, and a README that already admits its gaps in a “Not implemented yet” section — which is more honesty than most projects at this stage.
